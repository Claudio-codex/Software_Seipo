## Language

Always respond to the user in Spanish (siempre responde en español), including explanations, summaries, questions, and commit messages.

## Overview

SEIPO is a Java Swing desktop app for sales and inventory ("Sistema de venta e inventario") backed by a local MySQL database. Code, identifiers, UI text, and docs are in Spanish. Money is in Peruvian soles (`Datos.soles(...)`), and IGV (18% tax) is applied to every sale.

## Build & Run

No build tool (Maven/Gradle). The project is built from an IDE: IntelliJ (`Software_Seipo.iml` at the repo root, source root `SEIPO/src`) or NetBeans/Ant (`SEIPO/build.xml`, `SEIPO/nbproject/`). There are no tests and no linter.

- **Prerequisite:** MariaDB 12.3 (Windows service) or XAMPP's MySQL. The connection settings (`db.host`, `db.puerto`, `db.base`, `db.usuario`, `db.clave`) are read from `config.properties` in the **working directory** (the repo root; override with `-Dseipo.config=<path>`). That file is git-ignored. If it is missing, `ConexionBD` creates it with XAMPP defaults (`localhost`, `3306`, `seipo_db`, `root`, empty password). `config.ejemplo.properties` is the committed template (user `seipo`, practice password `Seipo2026`). NetBeans runs from the repo root via `run.working.dir=..` in `nbproject/project.properties`. On MariaDB for Windows, `root` may use GSSAPI (Windows auth), which Connector/J can't load, so use the `seipo` user.
- **Entry point:** `seipo.vista.Login` (`main`). Default login: `admin` / `123` (seeded by `ConexionBD`).
- **Backups:** `respaldo.bat` (repo root, CRLF line endings enforced by `.gitattributes`). It reads `config.properties`, finds `mariadb-dump.exe`/`mysqldump.exe` (the optional `respaldo.dump` key, then `C:\Program Files\MariaDB 12.3\bin`, then `C:\xampp\mysql\bin`, then the PATH), passes the password through `MYSQL_PWD`, writes `respaldos\<base>_yyyy-MM-dd_HHmm.sql` (git-ignored) and exits with 1 on failure so Task Scheduler records it. `SEIPO/bd/seipo_db.sql` must be imported with `mariadb.exe`/`mysql.exe` from `cmd` (HeidiSQL fails with it).
- `seipo.modelo.ConexionBD#main` checks the connection and creates the schema.
- The required jars (MySQL Connector/J, FlatLaf, OpenPDF, Apache POI and its dependencies) are in `SEIPO/lib`. IntelliJ uses them through the `seipo-lib` library, and NetBeans lists them in `javac.classpath` in `nbproject/project.properties`. If you add a jar, update both.
- Command-line compile/run (connector jar path required):
  ```
  javac -d out -cp <mysql-connector-j.jar> $(find SEIPO/src -name "*.java")
  java -cp "out;<mysql-connector-j.jar>" seipo.vista.Login   # ':' separator on Unix
  ```
- `out/` and `SEIPO/out/` contain IDE build output (some of it is committed). Don't edit them.

## Architecture

The app is a simple three-package MVC under `SEIPO/src/seipo/`:

- **`modelo`**
  - `ConexionBD.obtenerConexion()` is the only way code gets a DB connection. It loads `config.properties` once per run. The database name is configurable (validated as `[A-Za-z0-9_]+` because it goes into the `CREATE DATABASE`/`USE` SQL), so don't hard-code `seipo_db` in code. `ConexionBD.mensajeError(SQLException)` turns connection errors into a message saying what to check (service down or wrong host/port, wrong user/password, missing grants, unsupported auth plugin); `Login` shows it. The **first successful call in each run** executes `inicializarBaseDatos()` (guarded by the `esquemaListo` flag; if MySQL is down it retries on the next call), which runs `CREATE DATABASE/TABLE IF NOT EXISTS` and seeds the admin user. This makes the schema self-bootstrapping, so schema changes go in that SQL array. `CREATE TABLE IF NOT EXISTS` does not alter tables that already exist, so a new column on an existing table also needs an `ALTER TABLE ... ADD COLUMN` through `agregarColumna` (it ignores MySQL error 1060, duplicate column). See `actualizarUsuarios` for an example. Indexes are added the same way with `agregarIndice` (ignores error 1061) in `crearIndices`; `ventas` has indexes on `(turno_id, estado)`, `(cliente_id, estado)` and `(fecha, estado)`, which the shift, client and report queries rely on.
  - `Sesion` holds the logged-in user (id, name, role). There are two roles, `ADMINISTRADOR` and `PERSONAL`. `Principal` only builds `PanelReportes`, `PanelPagos` and `PanelUsuarios` for administrators.
  - `Datos` holds shared constants (`IGV`, `STOCK_BAJO` low-stock threshold, the `dd/MM/yy` date format), the `ProductoVenta` value object, and the currency formatter.
- **`controlador`**: one controller per screen (`ControladorVentas`, `ControladorProductos`, etc.). Each one opens its own connection with try-with-resources, uses plain JDBC `PreparedStatement`s, throws `SQLException` up to the view, and returns small nested `*VO` classes with public fields.
- **`vista`**: Swing views. `Login` opens `Principal`, a `JFrame` with a side menu and a `CardLayout` of `Panel*` screens. `Principal.mostrar()` calls each panel's `refrescar()` when that panel is shown, so new panels need a `refrescar()` and a case in that method. Each section is registered in `Principal` with a menu group (OPERACIÓN, INVENTARIO, GESTIÓN) and a description, which the header shows. `UI` holds the visual theme and the widget factories:
  - Dark theme: FlatLaf, installed by `UI.instalarTema()` in `Login.main`, before any window is created.
  - Palette constants (`FONDO`, `SUPERFICIE`, `TEXTO`, `TEXTO_SECUNDARIO`, `ACENTO`, `BORDE`, `FILA_*` row tints). Use these instead of hard-coded colors, and never use light colors such as `Color.WHITE` for backgrounds.
  - Fonts via `UI.fuente(estilo, tamaño)`.
  - Buttons: `boton` (main action), `botonSecundario`, and `botonPeligro` (reject/remove).
  - Tables: `modelo` (read-only model), `tabla`, `colorearFilas` (tints rows that need attention), `columnaAncha`.
  - Layout: `tarjeta`, `ayuda`, `base`.

  `Graficos` uses the same palette. `ExportadorReporte` keeps its own light colors for PDF and Excel.

Domain notes:
- Stock is tracked per batch in `lotes` (FEFO). `productos.stock` is a cached total that **must always equal** `SUM(lotes.cantidad)` for that product, so any code that changes stock updates both in the same transaction. Stock only comes in through `ControladorInventario.registrarRecepcion` (receipt with a delivery guide, `recepciones`). New products start at 0. Batches with no expiry date have `fecha_vencimiento NULL` and sort last.
- A sale (`ControladorVentas.cobrarVenta`) runs as one transaction: it requires an open cash shift (`turnos`) for the logged-in user, inserts into `ventas` (subtotal, discount, total, client, user, shift, cash received) and `detalle_ventas`, takes stock from batches in FEFO order (soonest expiry first, `FOR UPDATE`), skips expired batches, decrements `productos.stock`, records each batch used in `venta_lotes`, and logs one `movimientos` row per batch used. If the non-expired stock is not enough, it rolls back. The stock shown in Ventas is the sellable stock (non-expired batches) and does not include expired units.
- Cash shifts (`ControladorCaja`, `PanelCaja`): each user has at most one `ABIERTO` shift, opened with the starting cash. Closing stores `efectivo_esperado` (starting cash + non-voided cash sales) and `efectivo_contado`; the difference is shortage/surplus. A user closes their own shift; an administrator can close anyone's. Ventas totals per payment method come from `ventas.forma_pago` (`Datos.FORMAS_PAGO`, cash is `Datos.EFECTIVO`).
- Voiding (`ControladorVentas.anularVenta`): administrator only, and only while the sale's shift is still open (so a closed cash count never changes). It sets `ventas.estado = 'ANULADA'`, returns the units to the same batches via `venta_lotes`, and logs an `Anulación` movement. Every query that sums sales (reports, shift totals, client purchase counts) must filter `estado = 'COMPLETADA'`.
- Payment methods are `Datos.FORMAS_PAGO` = Efectivo and Yape o Plin (`Datos.YAPE_PLIN`); card payments were removed at the user's request (they may come back if the course instructor asks; the old code is in git history). `cobrarVenta` rejects any other method. Shift totals (`TurnoVO.totalVendido`) and reports still add old sales with other methods, so legacy data keeps adding up.
- Digital payments (`ControladorPasarela`, `DialogoPasarela`): Yape o Plin goes through a **simulated** payment gateway (no external service). `solicitarCobro` creates a `transacciones_pago` row `PENDIENTE` with a random token; `autorizarBilletera` (with simulated latency, run in a `SwingWorker`) set it to `APROBADA` (with an authorization code) or `RECHAZADA` (with the reason). Test data: any 9-digit phone starting with 9 and any 6-digit approval code is approved, except `000000`. Only the last 3 digits of the phone are stored. `cobrarVenta` receives the token, checks inside its transaction that it is `APROBADA`, unused, same user, same payment method and same amount, and links it via `venta_id`. If the sale fails after approval, the view calls `revertir` (`REVERTIDA`); voiding a sale sets its payment to `REEMBOLSADA`. Gateway settings and the business data (name, RUC, address) live in the key/value table `configuracion` (seeded by `ConexionBD`, edited by the administrator in `PanelPagos`); the gateway secret key is stored in plaintext. If the gateway is disabled, Ventas disables the Tarjeta and Yape o Plin buttons.
- Receipts (`ControladorComprobantes`, `DialogoComprobante`, `ExportadorComprobante`): every sale emits a `comprobantes` row in the same transaction: `FACTURA` series `F001` when the client has an 11-digit RUC, otherwise `BOLETA` series `B001`, numbered with `MAX(numero) + 1 ... FOR UPDATE` per series. It stores a snapshot of the issuer data and a verification code (`codigoVerificacion`, SHA-256 of RUC, number, total and issue time). The dialog shows a dark HTML preview, prints a light version and saves an 80 mm PDF ticket sized to its content. Caja opens the receipt as the sale detail. Receipts are marked as test documents and are not sent to SUNAT.
- Client VIP discount (`ControladorClientes.ClienteVO.porcentajeVIP`) depends on that client's completed purchases; Ventas applies it automatically when the client is chosen.
- Write-offs (`mermas`, `ControladorMermas`) are tied to a batch. Anyone can register one, and it starts as `PENDIENTE`. While pending, its units are reserved: `RESERVADO_EN_LOTE` is subtracted from the sellable stock in `ControladorVentas` and from what is left to write off. Only an administrator can move a write-off to `APROBADA`, which in one transaction decrements the batch and `productos.stock` and logs a `Merma` movement, or to `RECHAZADA`, which releases the reservation. The write-off stores `precio_unitario`, so the value lost doesn't change if the price changes later. `PanelMermas` exports a period report (by `solicitado_en`, via `listarMermas(desde, hasta)`) to PDF/Excel with `ExportadorReporte`; lost value and units count only `APROBADA` write-offs, and the PDF ends with signature lines (`Reporte.firmas`; `Reporte.nota` adds a note under the indicators).
- Stock alerts (`ControladorCompras.listarAlertas`) use the sellable stock compared against `productos.stock_minimo` and `stock_maximo` (NULL means no limit): Agotado, Stock bajo, or Sobrestock. The Inventario summary counts the same alerts. Purchase orders (`ordenes_compra` + `detalle_ordenes`) go `PENDIENTE` → `APROBADA` (administrator) → `RECIBIDA`, or to `RECHAZADA`. Units on pending or approved orders count as "en pedido", and the suggested quantity subtracts them. An order is received through `ControladorInventario.registrarRecepcion(..., ordenId)`, which creates the batches and marks the order in the same transaction. `Principal` refreshes the alert count on the Compras button with a `javax.swing.Timer` and when switching screens. The sale total is `Datos.totalVenta(subtotal, discount)`: `(subtotal - discount)` plus `Datos.igvVenta` (IGV rounded to cents), then rounded **down** to 10 céntimos, because 1 and 5 céntimo coins are not used (the rounding favors the customer). `Datos.redondeoVenta` is the amount taken off, shown as "Redondeo". Both `ControladorVentas` and `PanelVentas` use these. Cash amounts (amount received, starting cash, counted cash) must be multiples of 0.10 (`Datos.esMontoEnMonedas`).
- `detalle_ventas` and `movimientos` store the product **name** (`producto_nombre`) rather than a foreign key to `productos`. `movimientos.fecha` is a `VARCHAR` formatted with `Datos.FECHA`.
- Passwords are stored in plaintext (`ControladorLogin`, `ControladorUsuarios`). `ControladorLogin` looks the user up by name and compares the password in Java, because the `utf8mb4_unicode_ci` collation would make an SQL comparison case-insensitive (usernames are case-insensitive, passwords are not). Deactivated users (`usuarios.activo = FALSE`) can't log in. `ControladorUsuarios.actualizarUsuario` stops the logged-in user from demoting or deactivating themselves, and keeps at least one active administrator.

The demo data in `SEIPO/bd/seipo_db.sql` is for a general store (bazar) that sells school supplies, cleaning products, hardware, kitchenware, accessories, toys, perfumes and watches. It sells no food and no clothing, so keep demo data and examples within those categories.
